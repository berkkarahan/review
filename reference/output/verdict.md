# Verdict (Phase 2.4)

**Effort never restricts the verdict.** `--effort` sets only how much the model thinks and how far it looks (`depth.thinking`, `depth.reach`). At `high`, `medium`, `low`, and `skim`, the lead reaches one of the same three standardized PR verdicts (`APPROVE`, `COMMENT`, `REQUEST_CHANGES`) after the review completes.

**Post-review decision (`level=PR`, Phase 2.4).** At `level=PR`, `scripts/breaker.py` does **not** mechanically compute a verdict or GitHub event from finding counts. Instead:
1. Phase 2.3 (`scripts/merge_findings.py finalize`) validates schema/carry/safety-floor integrity and computes `open` counts, `unsatisfied` AC count, `declined_blocking`, `complete`, informational `band`, and `blocking_signals` (`open CRITICAL`, `Missing or Contradicted AC`, `breaking change with no migration`, `open HIGH`, `declined_blocking`, `NOT ASSESSED` lanes), returning `verdict_pending: true`.
2. After `finalize` and any `eval_followup_needed` finish, the lead evaluates the **entire PR holistically** — `intent.md`, `pr.json` (title, description, draft, size), finalized `post` findings (`reported.json`), `chat-only.json` observations, `ac_matrix`, `high_risk`, `safety_alerts`, `gaps`, `blocking_signals`, and `complete` — and chooses one final verdict **regardless of how many or which inline comments are made**:
   - **`APPROVE`**: The change is safe and ready to merge. Valid with zero inline comments, only `LOW` items, **or** non-blocking inline comments (`MEDIUM` / `QUESTION` / suggestions) that do not need another review round.
   - **`COMMENT`**: Share observations, questions, or advisory feedback without approving or blocking merge. Valid with any number of inline comments (zero, minor, medium, questions, or even blocking observations when commentary is appropriate instead of a merge block), or when coverage gaps / draft state / open questions prevent approval.
   - **`REQUEST_CHANGES`**: The PR must be revised before merge. Valid when open `CRITICAL`/`HIGH` defects, unmet ACs, unmigrated breaking changes, **or PR-wide architectural/scope flaws (even with zero inline comments)** make the PR unsafe or wrong to merge as-is.
3. **Soft guardrail.** Choosing `APPROVE` while `blocking_signals` is non-empty (`open CRITICAL`, `open HIGH` confirmed/plausible/unverified, `Missing`/`Contradicted` AC, unmigrated breaking change, `declined_blocking > 0`, or `NOT ASSESSED` lane) requires a non-empty `override_reason` explaining why approval is still justified. `merge_findings.py verdict` / `breaker.py` exits `1` (`INVALID:`) if `override_reason` is missing, and sets `verdict_overrode_blocking: true` + a warning note when present. At posting time (`output/posting.md`), the user sees a warning when approving over blocking signals and can still choose any allowed event.

- **What counts in `open` and `blocking_signals`.** `breaker.py` counts open `todo` findings with `origin: new` (or omitted) and `eval_disposition: post` (or omitted), including `plausible` and `unverified` `CRITICAL`/`HIGH` findings. It does not count `refuted` items, `eval_disposition` `chat-only` or `drop` items, `origin: existing` items, `status: fixed` or `status: declined` items (except new/standing blocking declines in `declined_blocking`), or (at `level=PR`) `introduced_by_pr: pre-existing` items. Both medium Pareto cuts and Phase 3 Gate G7 truncation run *after* `finalize` and never alter `open`, `blocking_signals`, or the verdict (`effort/levels.md`).
- **Single-phrase STE headers & verdict enum.** The report H2 heading keeps the single-phrase traffic-light format (`## 🔴 Not ready to merge`, `## 🟡 Comments for the author`, `## 🟢 Ready to merge`; for `author_is_me`: `Not ready for review`, `Comments for self-review`, `Ready for review`), while the standardized verdict enum (`APPROVE` | `COMMENT` | `REQUEST_CHANGES`) appears in the report footer, JSON outputs, `verdict-decision.json`, `breaker-input.json`, and `--non-interactive` JSON.
- **Persona voice keys & `hold_event`.** `voice.*` keys come from the persona file (`persona_path` in `bundle-summary.json`) frontmatter. For `verdict == "REQUEST_CHANGES"`, `event` defaults to `voice.hold_event` (`REQUEST_CHANGES` default, or `COMMENT` for reviewers who hold PRs with comment reviews); for `COMMENT`, `event` is `COMMENT`; for `APPROVE`, `event` is `APPROVE`. At posting time (`output/posting.md`), the user can switch freely among `APPROVE`, `COMMENT`, and `REQUEST_CHANGES` when `!author_is_me`.
- **`author_is_me`.** At `level=PR`, `event` is always forced to `COMMENT`, because GitHub rejects `APPROVE` and `REQUEST_CHANGES` on your own PR. The review `verdict` itself still records `APPROVE` / `COMMENT` / `REQUEST_CHANGES` and uses the self-review phrase. At `level=CODEBASE`, `event` is always `NONE` (even when `author_is_me` is true).

**`level=CODEBASE` mapping (unchanged).** With `--level CODEBASE`, `finalize` / `breaker.py` keeps deterministic codebase health verdicts (`NEEDS ACTION` / `"Codebase needs urgent fixes"`, `IMPROVEMENTS RECOMMENDED` / `"Codebase needs targeted improvements"`, `HEALTHY` / `"Codebase is in good shape"`), counts `pre-existing`/`codebase` findings normally, rejects `--effort skim` (`valid: false`), always sets `event` to `"NONE"`, and skips Phase 2.4 (`merge_findings.py verdict` rejects `CODEBASE` with exit `2`).

**Record and validate the PR verdict (Phase 2.4).** Run:
```
python3 scripts/merge_findings.py verdict <bundle_dir> \
  --verdict <APPROVE|COMMENT|REQUEST_CHANGES> \
  --reason "<one concise STE sentence>" \
  [--override-reason "<one concise STE sentence>"] \
  [--file <bundle_dir>/verdict-decision.json]
```
The script scrubs PII (`@handles`, emails), writes `<bundle_dir>/verdict-decision.json`, embeds `"decision"` into `<bundle_dir>/merged.json` and `<bundle_dir>/breaker-input.json`, validates safety floor + carry + Soft Guardrail via `breaker.py` (`require_verdict=True`), and computes `event`, `next_step`, `phrase`, and `zero_findings_fast_path`.

**Run `breaker.py` standalone.** Replays an archived or finalized `<bundle_dir>/breaker-input.json` (which already embeds `"decision"` at `level=PR`), or accepts explicit CLI flags:
```
python3 scripts/breaker.py <bundle_dir>/breaker-input.json [--level PR|CODEBASE] --effort <level> [--hold-event <event>] [--author-is-me] [--in-profile] [--ci <value>] [--pre <bundle_dir>/candidates-pre-eval.json] [--previous <bundle_dir>/previous.json] [--verdict APPROVE|COMMENT|REQUEST_CHANGES --verdict-reason "<text>" [--verdict-override-reason "<text>"]] [--verdict-file <path>] [--require-verdict]
```
- **Output.** JSON with `valid`, `level`, `effort`, `open`, `unsatisfied`, `declined_blocking`, `complete`, `band`, `blocking_signals`, `verdict`, `verdict_pending`, `verdict_reason`, `verdict_override_reason`, `verdict_overrode_blocking`, `emoji`, `phrase`, `event`, `next_step`, `reasons`, `notes`, and `invalid`.
  - `next_step` at `level=PR`: `fix` (`REQUEST_CHANGES`), `done` (`APPROVE`), `rerun` (`COMMENT` with a `NOT ASSESSED` lane), `document` (`COMMENT` when complete), or `null` (verdict pending or input invalid).
  - `next_step` at `level=CODEBASE`: `fix` (`NEEDS ACTION`), `rerun` (`NOT ASSESSED` lane), `document` (`IMPROVEMENTS RECOMMENDED`), `done` (`HEALTHY`), or `null` (invalid).
- **Invalid input.** On exit `1`, `breaker.py` / `merge_findings.py verdict` prints one `INVALID:` line per problem on stderr. Fix only what each line names (for example, supply `--override-reason` or revise the verdict) and re-run once. Never change a severity, status, AC verdict, or finding set to make validation pass. After a second failure, stop and show the lines to the user.
