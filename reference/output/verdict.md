# Verdict (Phase 2.3)

**Effort never changes the verdict.** The same table gives the verdict, the event and `next_step` at `high`, `medium`, `low` and `skim`. Any open CRITICAL, unmet acceptance criterion, unmigrated breaking change or open HIGH gives REQUEST CHANGES. Any MEDIUM or QUESTION gives APPROVE WITH COMMENTS. Otherwise the verdict is APPROVE. A `plausible` or `unverified` CRITICAL/HIGH counts like a confirmed one. The quality-gate band is information only.

**Source of the verdict.** The script `scripts/breaker.py` computes the verdict, the default event, the open counts, the AC count, the completeness and the quality-gate band, at every effort level and for both `level=PR` and `level=CODEBASE`. `scripts/merge_findings.py finalize` invokes `breaker.py` in-process and writes both `<bundle_dir>/merged.json` and `<bundle_dir>/breaker-input.json`. The lead uses the breaker output as it is and must not compute these values again. The verdict rules (the condition table for each effort level, and the quality-gate banding) are in the docstring of `scripts/breaker.py`. The lead does not need to read them.

- **What counts.** The verdict counts open `todo` findings with `origin: new` (or omitted): verified CRITICAL and HIGH findings, and the MEDIUM and QUESTION findings evaluated as `post` (`eval_disposition: post` or omitted). It counts a `plausible` or `unverified` CRITICAL/HIGH. It does not count `refuted` items, `eval_disposition` `chat-only` or `drop` items (Phase 2.2 evaluation), `origin: existing` items, `status: fixed` or `status: declined` items (though new blocking declines count in `declined_blocking`), or (at `level=PR` only) `introduced_by_pr: pre-existing` items. Both medium Pareto cuts and Phase 3 Gate G7 truncation run *after* `breaker.py` and change only what the report/PR posts show, never the verdict (`effort/levels.md`). A review with only `chat-only` items gives `APPROVE` (`HEALTHY` at `CODEBASE`). At `high`, `medium`, and `skim`, a `post` QUESTION gives `APPROVE WITH COMMENTS` (`IMPROVEMENTS RECOMMENDED` at `CODEBASE`), because the reviewer cannot judge the change until the author answers; this holds at every effort. `declined_blocking` and `NOT ASSESSED` also cap `APPROVE`.
- **Persona voice keys.** `voice.*` keys are read from the persona file (`persona_path` in `bundle-summary.json`) frontmatter. A missing key uses the default shown.
- **Holding a PR without Request Changes.** Some owners hold a PR with a COMMENT review and never use Request Changes. For them, `voice.hold_event: COMMENT`, and `REQUEST_CHANGES` is offered only as an explicit option at posting time.
- **Mechanical verdict.** The verdict itself stays mechanical, and the chat report states it plainly.
- **`author_is_me`.** At `level=PR`, the event is always `COMMENT`, because GitHub rejects approve and request-changes reviews on your own PR, and the verdict is framed as "ready / not ready for review". At `level=CODEBASE`, `event` is always `NONE` (even when `author_is_me` is true).

**`level=CODEBASE` mapping.** With `--level CODEBASE`, `breaker.py` counts `pre-existing`/`codebase` findings normally, rejects `--effort skim` (`valid: false`), maps verdicts and phrases to codebase health states (`REQUEST CHANGES` -> `NEEDS ACTION` / `"Codebase needs urgent fixes"`, `APPROVE WITH COMMENTS` -> `IMPROVEMENTS RECOMMENDED` / `"Codebase needs targeted improvements"`, `APPROVE` -> `HEALTHY` / `"Codebase is in good shape"`), and always sets `event` to `"NONE"`.

**Run the breaker.** `scripts/merge_findings.py finalize` runs `breaker.py` automatically at every effort level (after Carry G9 when enabled, and before the Pareto cut). To run standalone on `<bundle_dir>/breaker-input.json` or `<bundle_dir>/merged.json`:
```
python3 scripts/breaker.py <bundle_dir>/breaker-input.json [--level PR|CODEBASE] --effort <level> [--hold-event <event>] [--author-is-me] [--in-profile] [--ci <value>] [--pre <bundle_dir>/candidates-pre-eval.json] [--previous <bundle_dir>/previous.json]
```
- **Input.** `merged.json` / `breaker-input.json` is `{"level": "PR|CODEBASE", "findings": [...], "ac_matrix": [...], "lanes": [...], "folded": [...]}` (it may also embed optional `"effort"`, `"hold_event"`, `"author_is_me"`, `"in_profile"`, `"ci"`, which CLI flags override). Put these items in it:
  - the evaluated findings (`eval_disposition: post` only, or marked with `eval_disposition` so `breaker.py` skips `chat-only` and `drop`; carried `fixed` and `declined` items are included when `--carry` ran)
  - the AC rows with their statuses after verification
  - one entry for each lane that ran (including `evaluation`): `status` is `returned`, `abstained` or `NOT ASSESSED`, and the last two need a `reason` (never pass `"lane": "lead"`)
  - `folded`: the lanes that were folded into another lane

  `--in-profile` and `--ci` apply only at `skim`. `--pre` is the **post-merge, post-verification, pre-evaluation** set (`candidates-pre-eval.json`) with `verified` set, used for the safety-floor check. `--previous` is `previous.json` (or the earlier `findings.json`).
- **Output.** The script prints JSON with `valid`, `level`, `effort`, `open` (a count for each severity), `unsatisfied`, `declined_blocking`, `complete`, `band`, `verdict`, `emoji`, `phrase`, `event`, `next_step`, `reasons`, `notes` and `invalid`. `next_step` is `fix` (REQUEST CHANGES), `rerun` (a lane is NOT ASSESSED), `document` (only non-blocking or declined items remain: fix them or record a decline reason, then stop), or `done`. `--in-profile` and `--ci` have no effect on the verdict or the event. Print `phrase` and the reason. It never changes the findings or any file.
- **Not counted.** The script does not count a finding that is `refuted`, a finding with `eval_disposition` `chat-only` or `drop`, a finding with `origin: existing`, a finding with `status: fixed` or `status: declined` (except `declined_blocking`), or (at `level=PR`) `introduced_by_pr: pre-existing`. A finding with no `status` is `todo`. A finding with no `origin` is `new`.
- **Invalid input.** If the script exits with 1, it prints one `INVALID:` line for each problem. Correct only what each line names, and run the script again. Never change a severity, a status, an AC verdict or the set of findings to make the script pass. After a second failure, stop and show the lines to the user.
